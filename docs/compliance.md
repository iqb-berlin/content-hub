# Compliance reports

Compliance reports are generated by GitHub Actions or the local scan runner and
are not committed to the repository. This keeps generated raw data out of the
source history while retaining reproducible evidence for dependency changes and releases.

## Pull requests

The `Compliance` workflow runs when a dependency manifest, lockfile, license,
or the workflow itself changes. It creates CycloneDX JSON SBOMs for the
backend, frontend, and Keycloak extension. The resulting `dependency-sboms`
artifact is retained for 30 days. The same job verifies that the canonical
Apache-2.0 license text and package declarations remain consistent. It also
enforces `compliance/dependency-license-policy.json` against every component in
the three runtime SBOMs. The Keycloak runtime BOM excludes Maven `provided`
dependencies, which are supplied by the Keycloak platform and are not bundled
in the shaded provider JAR. A separate `keycloak-altcha-platform.json` retains
the complete inventory, including those platform dependencies, for human review.
A dependency with missing metadata or without approved
license terms blocks the pull request. Version-specific metadata
overrides and reviewed exceptions are explicit; an update to such a component
therefore requires another review instead of silently inheriting the decision.
The same generator and policy check run in the CI security job required by the
protected `release-gate`, so a license-policy failure cannot be bypassed merely
because the separate artifact workflow is not a required check.

Dependabot checks npm, Maven, Python, Docker and GitHub Actions every Monday.
Minor and patch updates are grouped per ecosystem and manifest directory;
major updates remain separate. Security updates are grouped separately from
routine version updates. External GitHub Actions are pinned to immutable full
commit SHAs, while comments retain the readable release tag. Dependabot updates
the SHA when a new Action release is selected.

## External code provenance (SCANOSS)

The separate `External code provenance` workflow is started **manually for a
release or a deliberate provenance review**. It does not call the external API
on every pull request or on a weekly schedule. Each run scans a clean archive of
the entire tracked repository, including tests, fixtures and vendored Keycloak
theme scripts. SCANOSS's default file-type and directory exclusions still apply.
Dependency inventories and the weekly local ScanCode scan remain automatic.

The pinned Python client uses the free public `https://api.osskb.org` API without
an API key. Fingerprints and file metadata (including paths) leave the runner;
raw source text is not uploaded. The public service may have availability or
throughput limits. A failed, rate-limited or invalid scan remains incomplete and
fails its manually started check. It is never presented as a clean result.
Automatic retries are disabled to avoid repeated calls during a limit window.
A successful complete report can be reused for the **same source commit** after
human review. Local scanning also uses the public API and respects its limits;
it is not an offline alternative or a way to evade a quota.

For a dedicated or self-hosted endpoint, set the repository variable
`SCANOSS_API_URL`. If that endpoint requires authentication, store the token in
the `SCANOSS_API_KEY` Actions secret. The workflow passes the secret only through
the client's `--key` option and continues to use the public endpoint when the
variable is absent.

The `scanoss-code-provenance` artifact retains raw JSON when available, a
summary, status, scan log, scanned-file list, Git revision and tool version for
30 days.
Findings require human assessment: reviewers must examine source URLs, actual
licenses and attribution requirements before merging. A match can be legitimate reuse,
common code or the project's own public code. Document the review decision in
the pull request. The job summary and `status.txt` distinguish a completed scan
from an unavailable scan. No matches do not establish originality or
rights clearance.

For a local check, install `compliance/scanoss-requirements.txt` in a virtual
environment, then run:

```sh
scanoss-py scan --skip-settings-file --apiurl https://api.osskb.org \
  --threads 1 --retry 0 -o results.json <source-directory>
```
Read [contribution guidance](../CONTRIBUTING.md) before submitting AI-assisted code.

## Scheduled and manual scans

Every Monday, and whenever the workflow is started manually, ScanCode scans a
clean archive of the complete source tree for license, copyright, and package
metadata. The `source-license-scan` artifact is retained for 90 days.

A manual workflow run can additionally enable the Dolos similarity scan. It
compares TypeScript files inside this repository and retains only summary CSV
files for 30 days. Similarity results are indicators for human review; they do
not establish authorship, plagiarism, or a license violation.

## Releases

A release candidate requires complete SCANOSS, ScanCode and dependency reports
for the exact source commit, plus a completed human review. Choose one of the
two evidence routes below. A local report is accepted only with validated scope,
source hashes, an archived bundle and a human-reviewed bundle checksum. Failed
scans, old revisions, unchecked findings and expired workflow artifacts do not
meet the requirement. Scan failures keep clearance open.

### Local evidence (no paid service required)

Use a clean checkout of the final release commit. Install Python 3.12 and the
pinned requirements in `compliance/scanoss-requirements.txt` and
`compliance/scancode-requirements.txt` in a virtual environment; put its
`python3`, `scanoss-py` and `scancode` commands on `PATH`. Node 22/npm and Maven with Java 17
or newer are also needed for the SBOM generators. Then run:

```sh
commit="$(git rev-parse HEAD)"
evidence="reports/compliance-$commit"
python3 scripts/local_compliance.py scan --output-dir "$evidence"
python3 scripts/release_compliance.py draft-review \
  --commit "$commit" \
  --local-evidence "$evidence/local-compliance-evidence.zip" \
  --output "$evidence/review-draft.md"
```

The runner materializes every tracked file directly from Git objects, so ignored
build products and working files do not enter the scan. It stops at the first
failed tool and preserves logs and exit codes; a failed run does not produce a
release-usable bundle. ScanCode includes hashes for every tracked file. Its
small version-bound entry point clears ScanCode's built-in VCS-config exclusion
on this materialized snapshot, so tracked `.gitignore` files are included too.
No Git metadata is copied into that snapshot. SCANOSS
fingerprints must match those source bytes and every fingerprint must have an
API response. Its default exclusions are recorded in `excluded-files.txt` and
must be inspected during human scope review. This is full repository input, not
a claim that SCANOSS fingerprints every file format.

The ZIP contains the raw reports, source inventory, revisions, tool versions,
logs and a manifest with per-file SHA-256 checksums and the Git tree ID. It is
checked against Git again when preparing the review and collecting a release.
A complete existing report directory produced by this runner can be repackaged
without another API call with `local_compliance.py package --evidence-dir <dir>
--output <new-zip-path>`; reports for another commit cannot be reused.

To make these local files retrievable by release CI, publish them in this same
repository as an **evidence prerelease**, separate from application releases:

```sh
gh release create "compliance-$commit" \
  "$evidence/local-compliance-evidence.zip" "$evidence/review-draft.findings.json" \
  --repo iqb-berlin/content-pool-next --target "$commit" \
  --prerelease --latest=false --title "Compliance evidence $commit" \
  --notes "Scan evidence only; human rights review is pending."
```

Upload once; do not overwrite evidence that has already been reviewed. This
prerelease contains reports only and does not approve or deploy the application.
The generated issue record identifies its tag, fixed asset name and exact ZIP
checksum. A replacement asset, different checksum, unexpected archive member,
missing file, scan error or incomplete source inventory blocks release. CI only
downloads that fixed asset from this repository, never an arbitrary issue URL.

### GitHub workflow evidence (alternative)

Full successful `Compliance` and `External code provenance` workflow runs on the
same final commit are still accepted. Start both manually on `master` after
merging the release changes; a weekly Compliance run on the same commit can
also be used. Download the reports and generate the issue record:

```sh
python3 scripts/release_compliance.py draft-review \
  --commit <40-character-source-commit> \
  --scanoss <scanoss-code-provenance/results.json> \
  --scancode <source-license-scan/source-license-scan.json> \
  --scanoss-run-id <full-SCANOSS-run-id> \
  --compliance-run-id <full-Compliance-run-id> \
  --output <review-draft.md>
```

### Human clearance and release archive

A human maintainer creates a license review issue from the template using the
generated record from the chosen route. Do not mix local references and workflow
run IDs in one record.

The draft command writes a pending record and a companion `.findings.json` inventory
with source details; it never approves a finding. Inspect that inventory and the
raw reports, then paste the draft’s one JSON record into the issue. Every SCANOSS match, ScanCode license detection and
historical baseline finding needs a reason, evidence and one resolution:
`standard-pattern`, `licensed-reuse`, `independent-origin` or `removed`.
Licensed reuse additionally needs the applicable license. An accepted-risk note
or a missing original is not clearance. For replacement code, document its
independent origin; do not merely rewrite code to reduce a scanner match.

The `reviewer` is the GitHub login of the human maintainer who completes and
closes the issue. The issue must be owned by a repository maintainer and closed
as completed, with rights, assets, notices and software scope checks confirmed.
Editing or commenting after completion requires reopening and completing the
record again, so the recorded human decision cannot be reused for later edits.
The existing protected production environment supplies the final human approval;
its reviewer configuration must be maintained in GitHub. The validator checks
the record and identity, not whether a person's legal judgment was correct.
Unclear rights questions go to the responsible IQB legal contact.

Pass this issue URL as `compliance_review` when starting the release-candidate
workflow. Before image builds, the gate validates the issue, downloads the exact
workflow artifacts or the checksum-bound local bundle, verifies revisions and
completeness, reruns dependency policy, and checks all required decisions. No approval is manufactured by CI or an AI tool.

The resulting `compliance-evidence.tar.gz` contains the raw reports, workflow or
local bundle metadata, review issue snapshot, decisions, finding inventory and source revision. It is
attached to the GitHub prerelease and included in `SHA256SUMS`. Stable promotion
requires that archive and carries it forward without rebuilding. Release assets
have no Actions artifact expiry; retain them for the lifetime of the release and
include them in the organization's normal backup. Temporary scan artifacts keep
their 30/90-day limits, so archive them before they expire.

Syft also generates CycloneDX JSON SBOMs for both published container images and
both supported platforms from immutable image digests. They are checksummed and
attached to the prerelease, and carried forward on stable promotion.

The runtime archive and application images include the project Apache-2.0 text.
The frontend image also serves Angular's extracted `3rdpartylicenses.txt`.
Backend dependencies retain their shipped notices, and the shaded Keycloak
extension retains the project license and merged dependency LICENSE/NOTICE files.
Because the published ALTCHA and JSON-java JARs omit their license text, their
upstream version-specific notices are also included under `META-INF/licenses`,
with source URLs and checksums. Dependency version changes require updating this
notice manifest; CI verifies the versions and copied texts.
The root and package license copies are checked for consistency.

A completed review supports a statement such as: “Version X was checked for
software licenses and identifiable code provenance under the documented process;
no unresolved findings remained within that scope at the time of review.”
It is not a guarantee against third-party claims. Uploaded assessment content,
images and texts require their own rights process and are outside this review.

## Costs and availability

No paid scan subscription is required by the default configuration. OSSKB is
currently free on a best-effort basis and can rate-limit clients; it does not
guarantee accuracy or availability. Do not evade limits. Retry later or explicitly
configure an approved service. Complete local evidence is accepted by the process
above after human review; it does not remove the public API limit or replace
rights review. No paid API key is required by either default route.

Standard GitHub-hosted runners for this public repository are currently free.
Artifact/cache quotas and repository visibility changes can affect costs. Check
organization billing budgets and retain release evidence without accumulating
unneeded temporary artifacts. These conditions are not a promise of perpetual
free hosting; human review also requires staff time.

Sources: [OSSKB terms](https://www.softwaretransparency.org/terms),
[GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions),
[Apache-2.0 distribution conditions](https://www.apache.org/licenses/LICENSE-2.0).

## Tooling

The pipeline uses open source tools with pinned versions:

- CycloneDX for npm 6.0.0 (Apache-2.0)
- CycloneDX Maven plugin 2.9.3 (Apache-2.0)
- ScanCode Toolkit 32.5.0 (Apache-2.0), with compatible Pluggy 1.6.0 pinned
- SCANOSS Python client 1.54.2 (MIT)
- Syft 1.51.1 (Apache-2.0)
- Dolos 2.9.3 (MIT)

Generated reports describe the scanned revision only. A human review remains
necessary for unclear license expressions, missing metadata, copied source,
and project-specific exceptions.
